# Stage 03 — Bastion and two EC2 instances with the existing SSH key

[Français](../03-ec2.md) | [Home](../../README.md)

## Goal

Deploy **`lab6-ec2`** from Git Bash, reusing the first lab's EC2 key pair. CloudFormation references its **existing KeyName**: this stack does not generate, replace or delete a key. The private key file stays on your PC.

| Instance | Placement | Group | Public IPv4 |
|---|---|---|---|
| `lab6-bastion` | Bastion subnet, AZ A | `lab6-bastion-sg` | Yes |
| `lab6-web-a` | `10.10.11.0/24`, AZ A | `lab6-web-sg` | No |
| `lab6-web-b` | `10.10.12.0/24`, AZ B | `lab6-web-sg` | No |

All three use Amazon Linux 2023 x86_64, `t3.micro`, mandatory IMDSv2 and an encrypted 8 GiB gp3 root disk deleted with the instance. CPU credits use `standard` mode: performance may be limited after credits run out. This stage creates billable resources: EC2, EBS and the bastion public IPv4 add to the existing network.

## 1. Git branch and files

After merging stage 02:

```bash
git switch develop
git pull --ff-only origin develop
git switch -c infra/03-ec2
```

Extract the patch at the repository root, preserving paths. Review personal additions before replacing README files. Stages 01 and 02 stay deployed.

## 2. Find the existing key pair

```bash
aws ec2 describe-key-pairs \
  --query 'KeyPairs[].[KeyName,KeyType,KeyFingerprint]' \
  --output table --region us-east-2 --no-cli-pager
```

Select the **KeyName corresponding to the first lab's private key**. It is used for deployment; the private file path is used later for SSH. The script checks that this name exists in Ohio without reading the private key file. SSH tests will confirm that the file matches the selected pair.

If the pair no longer exists in AWS but you still have the private file, stop here: its public key can be reimported through CloudFormation while keeping the same private key. Do not generate a replacement key to work around this case.

## 3. Deploy

Replace `NOM_CLE_EXISTANTE` with the displayed name:

```bash
bash scripts/deploy-ec2.sh "NOM_CLE_EXISTANTE"
```

The script checks `lab6-network` and `lab6-security`, reads the VPC, subnet and group outputs, then validates and deploys the template. It waits for EC2 status checks to pass. Prerequisite stack names can also be supplied as arguments 2 and 3.

The AMI is resolved through AWS's public `/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64` parameter. A later update may resolve a newer AMI and replace instances: review the change before updating this stack. The template contains no secrets.

Expected: **`CREATE_COMPLETE`**, three `running` instances, the same KeyName on all three, web servers in two zones and a public IPv4 only on the bastion. EC2 checks do not yet prove SSH or application connectivity. Application installation will be automated later; no Python service on port 8080 is expected now.

On failure:

```bash
aws cloudformation describe-stack-events \
  --stack-name lab6-ec2 \
  --query 'StackEvents[?ResourceStatus==`CREATE_FAILED` || ResourceStatus==`UPDATE_FAILED`].[LogicalResourceId,ResourceStatusReason]' \
  --output table --region us-east-2 --no-cli-pager
```

Read the exact cause (permissions, quota, capacity, key, AMI) before retrying. If CloudFormation succeeds but the EC2 waiter fails, inspect the instances rather than blindly recreating the stack. Resources may already be running.

## 4. Configure SSH using the retained file

From Git Bash, supply the actual private file path. Adapt this example:

```bash
bash scripts/configure-ssh.sh "/c/Users/TonNom/.ssh/ta-cle-existante.pem"
```

The script reads current instance addresses and writes Git-ignored **`local/ssh_config`**. It handles paths containing spaces and uses ProxyJump for the private servers. It does not copy the key or modify your global SSH configuration.

The key stays on your PC, including when connecting to private servers. Agent forwarding is disabled. On the first connection, verify the host fingerprint before accepting it. Reuse the file permissions that worked during the first lab.

## 5. Test the three connections

These commands run `hostname` remotely and automatically return to the local terminal:

```bash
ssh -F local/ssh_config lab6-bastion hostname
ssh -F local/ssh_config lab6-web-a hostname
ssh -F local/ssh_config lab6-web-b hostname
```

The path is **PC → bastion → private server**. The second SSH connection is authenticated with the same key from your PC. If your public IPv4 changed since stage 02, rerun `bash scripts/deploy-security-groups.sh lab6-network` to update the SSH rule through CloudFormation. If the bastion receives a new IPv4 after a stop/start, rerun the SSH configuration script.

## Cleanup at the end of the lab

Delete future dependent resources first, including the ALB and its target group, then:

```bash
aws cloudformation delete-stack --stack-name lab6-ec2 --region us-east-2
aws cloudformation wait stack-delete-complete --stack-name lab6-ec2 --region us-east-2
```

CloudFormation terminates all three EC2 instances and deletes their root disks and interfaces created here. **The existing SSH key pair stays intact.** Network and security stacks stay deployed; clean those up after other resources that use them. NAT charges continue while it is provisioned.
