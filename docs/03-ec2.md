# Étape 03 — Bastion et deux EC2 avec la clé SSH existante

[English](en/03-ec2.md) | [Accueil](../README.fr.md)

## Objectif

Déployer **`lab6-ec2`** depuis Git Bash, en réutilisant la paire EC2 du premier lab. CloudFormation référence son **KeyName existant** : aucune clé n'est générée, remplacée ou supprimée par cette stack. Le fichier privé reste sur ton PC.

| Instance | Placement | Groupe | IPv4 publique |
|---|---|---|---|
| `lab6-bastion` | Sous-réseau bastion, AZ A | `lab6-bastion-sg` | Oui |
| `lab6-web-a` | `10.10.11.0/24`, AZ A | `lab6-web-sg` | Non |
| `lab6-web-b` | `10.10.12.0/24`, AZ B | `lab6-web-sg` | Non |

Les trois instances utilisent Amazon Linux 2023 x86_64, `t3.micro`, IMDSv2 obligatoire et un disque système gp3 chiffré de 8 Gio supprimé avec l'instance. Les crédits CPU sont en mode `standard` : les performances peuvent être limitées après épuisement des crédits. Cette étape crée des ressources facturables : EC2, EBS et l'IPv4 publique du bastion s'ajoutent au réseau existant.

## 1. Branche Git et fichiers

Après fusion de l'étape 02 :

```bash
git switch develop
git pull --ff-only origin develop
git switch -c infra/03-ec2
```

Extraire le correctif à la racine du dépôt en conservant les chemins. Relire les ajouts personnels avant de remplacer les README. Les étapes 01 et 02 restent déployées.

## 2. Retrouver la paire de clés existante

```bash
aws ec2 describe-key-pairs \
  --query 'KeyPairs[].[KeyName,KeyType,KeyFingerprint]' \
  --output table --region us-east-2 --no-cli-pager
```

Choisir le **KeyName correspondant à la clé privée du premier lab**. Il servira au déploiement ; le chemin du fichier privé servira ensuite aux connexions SSH. Le script vérifie que ce nom existe dans Ohio, sans lire le fichier privé. La correspondance entre cette paire et le fichier privé sera confirmée par les connexions SSH.

Si la paire n'existe plus dans AWS mais que tu conserves le fichier privé, arrêter ici : on pourra réimporter sa clé publique via CloudFormation en conservant la même clé privée. Ne pas générer de nouvelle clé pour contourner ce cas.

## 3. Déployer

Remplacer `NOM_CLE_EXISTANTE` par le nom affiché :

```bash
bash scripts/deploy-ec2.sh "NOM_CLE_EXISTANTE"
```

Le script vérifie les stacks `lab6-network` et `lab6-security`, récupère le VPC, les sous-réseaux et les groupes, puis valide et déploie le template. Il attend ensuite que les contrôles EC2 soient OK. Les noms des stacks prérequises peuvent aussi être fournis comme arguments 2 et 3.

L'AMI est résolue par le paramètre public AWS `/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64`. Une mise à jour ultérieure peut résoudre une AMI plus récente et remplacer les instances : examiner le changement avant de mettre cette stack à jour. Le template ne contient aucun secret.

Attendu : **`CREATE_COMPLETE`**, trois instances `running`, même KeyName sur les trois, deux zones pour les serveurs web et une IPv4 publique uniquement sur le bastion. Les contrôles EC2 ne prouvent pas encore la connectivité SSH ou applicative. L'application sera installée automatiquement dans une étape ultérieure ; aucun service Python sur 8080 n'est attendu ici.

En cas d'échec :

```bash
aws cloudformation describe-stack-events \
  --stack-name lab6-ec2 \
  --query 'StackEvents[?ResourceStatus==`CREATE_FAILED` || ResourceStatus==`UPDATE_FAILED`].[LogicalResourceId,ResourceStatusReason]' \
  --output table --region us-east-2 --no-cli-pager
```

Lire la cause exacte (permissions, quota, capacité, clé, AMI) avant de relancer. Si CloudFormation réussit mais que l'attente des contrôles EC2 échoue, inspecter les instances sans recréer la stack à l'aveugle. Les ressources peuvent déjà être en cours d'exécution.

## 4. Configurer SSH avec le fichier déjà conservé

Depuis Git Bash, indiquer le chemin réel de ton fichier privé. Exemple à adapter :

```bash
bash scripts/configure-ssh.sh "/c/Users/TonNom/.ssh/ta-cle-existante.pem"
```

Le script lit les adresses actuelles des instances et écrit **`local/ssh_config`**, ignoré par Git. Il conserve les chemins contenant des espaces et utilise ProxyJump pour les serveurs privés. Il ne copie pas la clé et ne modifie pas ton fichier SSH global.

La clé reste sur ton PC, même pour la connexion aux serveurs privés. Le transfert d'agent est désactivé. Lors du premier accès, vérifier l'empreinte de l'hôte avant d'accepter son enregistrement. Réutiliser les permissions du fichier qui fonctionnaient lors du premier lab.

## 5. Tester les trois connexions

Ces commandes exécutent `hostname` à distance puis reviennent automatiquement au terminal local :

```bash
ssh -F local/ssh_config lab6-bastion hostname
ssh -F local/ssh_config lab6-web-a hostname
ssh -F local/ssh_config lab6-web-b hostname
```

Le chemin est **PC → bastion → serveur privé**. La deuxième connexion SSH est authentifiée avec la même clé depuis ton PC. Si ton IPv4 publique a changé depuis l'étape 02, relancer `bash scripts/deploy-security-groups.sh lab6-network` pour mettre la règle SSH à jour via CloudFormation. Si le bastion reçoit une nouvelle IPv4 après un arrêt/redémarrage, relancer le script de configuration SSH.

## Résultats observés pendant le lab

Validation du 6 novembre 2026 :

| Vérification | Résultat |
|---|---|
| Stack `lab6-ec2` | `CREATE_COMPLETE` |
| Instances et contrôles EC2 | Trois instances `running`, contrôles réussis |
| Paire de clés | Clé du premier lab réutilisée sur les trois instances |
| SSH vers le bastion, commande `hostname` | Réussi |
| SSH vers web A via ProxyJump, commande `hostname` | Réussi |
| SSH vers web B via ProxyJump, commande `hostname` | Réussi |
| Placement des serveurs web | Deux AZ, aucune IPv4 publique |

Les connexions ont affiché un avertissement OpenSSH signalant que l'algorithme d'échange de clés de session négocié n'est pas postquantique. Les commandes SSH ont abouti. Le contrôle des algorithmes proposés par les serveurs et des mises à jour disponibles constitue un point de suivi ; aucune suppression de l'avertissement n'est ajoutée à la configuration. Voir [la documentation OpenSSH](https://www.openssh.org/pq.html).

RDS, l'application Python et l'ALB ne sont pas encore déployés : leur connectivité n'est pas validée par ces tests SSH.

## Nettoyage, à la fin du lab

Supprimer d'abord les futures ressources dépendantes, notamment l'ALB et son groupe cible, puis :

```bash
aws cloudformation delete-stack --stack-name lab6-ec2 --region us-east-2
aws cloudformation wait stack-delete-complete --stack-name lab6-ec2 --region us-east-2
```

CloudFormation termine les trois EC2 et supprime leurs disques système et interfaces créés ici. **La paire SSH existante reste conservée.** Les stacks réseau et sécurité restent présentes ; leur nettoyage se fait ensuite, après celui des autres ressources qui les utilisent. Le NAT reste facturé tant qu'il est provisionné.
